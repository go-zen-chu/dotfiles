# Code Review

コードやコミット、プルリクエストのレビュー時に、この規約を観点として差分を確認する。
目的は、テスト容易性・拡張性・保守性の高いコードを維持し、長期的に高い品質を保つこと。

## 使い方

1. レビュー対象の差分を把握する（変更ファイル・意図・影響範囲）。
2. 下記チェックリストの観点で差分を確認する。Go のコードには「Go の設計・テスト規約」も適用する。
3. 指摘は「観点 → 該当箇所 → なぜ問題か → 推奨する修正」の順で、根拠を添えて示す。
4. (MUST) の違反は、修正前に依頼者へ判断を求めるべき重要度として扱う。

## 一般的なソフトウェア設計ポリシー

1. (MUST) 指示がない場合、ソースコードのコメントや出力は全て英語にする。
2. まず対象プロジェクトのイディオム（慣習的パターン）に従い、次に各言語の標準的なイディオムに従う。
3. 疎結合かつ高凝集なモジュールを重視し、依存関係を明確化・制御する。モジュールは単一責任を実現する。
4. できるだけ各言語の標準ライブラリを利用し、外部ライブラリへの依存度を下げる。これにより脆弱性対応やバージョンアップによる後方互換性破壊への対応を減らす。
5. I/O ロジック（CLI・HTTP・ファイルアクセス）とビジネスロジックを明確に分離する。
6. インターフェース（または言語における同等の抽象化手段）でレイヤーやモジュール間の境界を明確にする。
7. インターフェースは宣言的に定義し、「どのように処理するか」ではなく「何をするか」を表す。利用者が「何ができるか」を端的に理解できるようにする。
8. (MUST) グローバルステートや暗黙的な副作用を禁止する。
9. (MUST) クラスやインターフェース間の依存関係は、コンストラクタベースの依存性注入で明示する。コンストラクタを見れば何に依存しているかを直ちに理解できる。
10. ソースコードは責任ごとにディレクトリを整理し（usecase, infra, cmd, domain など）、依存関係を明確にして安定性とモジュール性を実現する。
11. (MUST) 処理内容がわかる冗長なコメントは書かない。冗長なコメントなしで処理が分かる変数名・関数名を付ける。
12. (MUST) コメントを記載するのは次のケースに限定する。
    - `// TODO:` のように処理が未実装であることを示す。
    - 処理内容が直感的ではないもの。
    - 外部仕様に基づく実装の場合。
    - 運用などの知見からそうせざるを得なかったもの（Why Not）。
13. 変数のスコープはできるだけ小さくする。利用されるスコープの大きさに応じて変数名の長さを調整する。
14. (MUST) 全ての関数に、役割や目的を宣言的に示すトップレベルコメントを付ける。実装の詳細ではなく「何を実現するか」を説明する。
15. (MUST) 既に利用されている場合を除き、各言語で代表的な linter・formatter・testing framework を採用し、CI で常時チェックできるようにする。
16. (MUST) 外部から与えられた入力には validation を実施する。

## 一般的なテスト設計ポリシー

1. (MUST) テストコードは BDD を採用し、どのシナリオの際にどう振る舞うことを期待するかを定義する。`If xxx given, it should yyy` の形式で記述する。
2. 外部接続をする処理は最小のインターフェースを定義し、モックやスタブで代替できるようにする。
3. (MUST) 繰り返しになるテストデータの準備処理はヘルパー関数化し、テストコードを簡潔にする。
4. main 関数から呼び出される高レベルのエントリ関数のテストを優先する。ユーザーが実行するコマンドラインオプションや入力をテストで表現でき、カバレッジの広い統合テストになる。

## Go の設計ポリシー

1. (MUST) `context.Context` を必要とする関数では第一引数に挿入する。必ず呼び出し元から受け取り、自分で生成しない。
2. (MUST) 関数は `(result, error)` または同等の戻り値を持ち、error を適切に wrap する。wrap せずに返却することを禁止する。
3. (MUST) 構造体の初期化はコンストラクタ関数（`NewXxx`）を優先する。
4. (MUST) error の wrap には `fmt.Errorf` を利用する。
5. (MUST) panic は main 関数やテスト目的を除いて利用しない。error は必ずハンドリングし、呼び出し元でどう処理すべきかの判断を委ねる。
6. (MUST) log は標準ライブラリの `log/slog` を利用する。
7. (MUST) `log/slog` のログレベルを次のように使い分ける。
    - Error: アプリケーションに致命的な問題が発生しており、オペレーターがすぐに対応しなければならない。
    - Warn: 問題が発生しており、不具合発生時に原因のヒントとなるもの。
    - Info: 統計的な情報など、正常の範囲で稼働していることを示すログ。大量に流れ続けないよう注意する。
    - Debug: デバッグフラグ有効時のみ確認できる、詳細の挙動を示すログ。
8. プロジェクトのディレクトリ構成はユースケース駆動にする（cmd/, infra/, usecase/）。

## Go のテストポリシー

1. gotests（<https://github.com/cweill/gotests>）でテーブル駆動テストを定義する。
2. インスタンスの比較は go-cmp（<https://github.com/google/go-cmp>）を利用する。
3. uber-go/mock（<https://github.com/uber-go/mock>）で mock を生成する。インターフェースを定義するファイルの先頭に `//go:generate go run go.uber.org/mock/mockgen -source=$GOFILE -destination=mock_$GOFILE -package=$GOPACKAGE` を記載し、mock はインターフェースの契約テストと組み合わせる。
4. 大きなテストデータはテストファイルではなく testdata/ フォルダに格納し、テストコードから読み取る。
