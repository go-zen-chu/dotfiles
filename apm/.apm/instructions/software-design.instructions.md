# ソフトウェア設計の基本原則

テスト容易性・拡張性・保守性の高いコードを維持するための原則。
MUST に違反する場合は、変更を実施する前に依頼者へ判断を求めること。
具体的なコーディング規約・レビュー観点は `code-review` skill を参照する。

## 設計

- (MUST) 指示がなければ、ソースコードのコメント・出力は全て英語にする。
- まずプロジェクト、次に各言語の慣習的イディオムに従う。
- 疎結合・高凝集・単一責任。依存関係は明示し制御する。
- 標準ライブラリを優先し、外部ライブラリへの依存を下げる。
- I/O ロジック（CLI・HTTP・ファイルアクセス）とビジネスロジックを分離する。
- レイヤー/モジュール境界はインターフェースで宣言的に定義する（「どのように」ではなく「何をするか」）。
- (MUST) グローバルステートと暗黙的な副作用を禁止する。
- (MUST) 依存関係はコンストラクタベースの依存性注入で明示する。
- 責任ごとにディレクトリを整理する（usecase, infra, cmd, domain など）。
- (MUST) 命名で意図を伝え、冗長なコメントは書かない。コメントは TODO・非直感的な処理・外部仕様・Why Not に限る。
- (MUST) 全ての関数に「何を実現するか」を宣言的に示すトップレベルコメントを付ける。
- (MUST) 標準的な linter・formatter・testing framework を採用し、CI で常時チェックする。
- (MUST) 外部から与えられた入力は必ず validation する。

## テスト

- (MUST) BDD で `If xxx given, it should yyy` の形式で振る舞いを定義する。
- 外部接続は最小のインターフェースでモック/スタブに置換可能にする。
- (MUST) 繰り返すテストデータ準備はヘルパー関数化する。
- main から呼ばれる高レベルのエントリ関数のテストを優先する。
